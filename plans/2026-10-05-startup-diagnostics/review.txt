1. [high] Stop racing with Ready can skip runtime deletion — app/src-tauri/src/controller.rs:750
   Successful completion requires the current UI phase to be Ready. Stop sets Stopping, and Store::handle_event deliberately suppresses Ready while stopping. 2. [high] A temporary disconnect permanently fails an established runtime — app/src-tauri/src/controller.rs:526
   This deadline applies to every Booting state without an active startup worker. snapshot_app returns status=None when an agent request fails. Store::apply_snap then changes an established Ready runtime to Booting and uses the original pod start time. For pods older than 40 minutes, this immediately sets cleanup_failed. Later successful Ready snapshots cannot recover because apply_snap preserves the failed phase while that flag is set.
   Scenario: A runtime has been Ready for over 40 minutes, then one agent status request fails → the app reports startup timeout and requires Stop even after connectivity recovers.
   Fix: Track startup completion per runtime identity. Apply the resumed-start deadline only before that runtime first reaches Ready. Keep later connectivity failures recoverable through successful snapshots.
   (bug, confidence 10)
